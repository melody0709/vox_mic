一、结论

VoxType 的 Settings 并不是新框架做的 —— 它仍然是 Win32 原生控件 + 手写 GDI 主题（3448 行）。 它比我们好看，不来自"架构更先进"，而来自三件我们从来没做过的小事：

  1. 有 manifest，从而加载 comctl32 v6 → Tab / 滑杆 / 下拉框 / 复选框走 Win10 原生外观；
  2. 有 DPI 感知（PerMonitorV2 + WM_DPICHANGED + 缩放函数）；
  3. 有一层统一的颜色 / 字体 token（一张色板 + 一种字体 + 统一标高）。

其中第 1 条我们完全缺失：设置窗口里的 Tab、滑杆、下拉框、复选框现在画的是 Windows 95 经典外观。第 2 条也完全缺失（见 §三 专项核对）。 这两条改动面都很小，却是权重最高的两条差异。

VoxType 在本文中只承担一个作用：证明"这三件事在 Win32 原生控件上就够用"。 它的外观与色板不被采纳 —— 我们按自己的设计语言（浅色，见方案文档 §3）落地。 因此下文各处"对齐 VoxType"一律读作"借用它已验证过的机制"，不是"照它的样子做"。

三、核对 B：DPI 自适应 —— 是真的缺失，还是一直没有？ 四方取证，结论：从来没有

这一条值得单独取证，因为它很容易被误记成"以前有、被某次重构弄丢了"。结论是： VoxMic 从建立到现在，任何一次提交里都没有过 DPI 自适应代码，也从未有过 manifest 文件 —— 不是重构丢的，是从来没写过。四条互相独立的证据：

这份 manifest 是 MSVC 链接器在没有自定义 manifest 时自动生成的默认 UAC 段 —— 也就是说，我们从来没有写过 manifest，才会有这个结果。

那为什么"感觉是自适应的"？

三个很可能叠在一起的原因：

  • Windows 的 DPI 虚拟化在替我们兜底。DPI 不感知的进程会被系统按"虚拟 96 DPI"运行， 再由系统把整窗位图放大。表现是：窗口大小看起来正常、不崩、不缩小 —— 但整窗连同文字一起被拉伸，发虚。 "没坏"很容易被读成"有自适应"，其实恰好相反：真实的自适应不会模糊。
  • 托盘图标是 Explorer 画的，始终清晰。只有设置窗口受影响，容易忽略。
  • VoxType 确实有真 DPI 自适应（app.manifest 的 PerMonitorV2 + WM_DPICHANGED）， 两个项目容易记混。
影响范围
100% 缩放下完全看不出来；125% / 150% / 175% 缩放下，设置窗口整体发虚（含文字与边框）； 在笔记本外接显示器、且两块屏缩放比例不同的场景下最明显（拖动窗口时还会跳变后被拉伸）。

顺带发现（次要）：manifest 里连 supportedOS 都没有声明。 这会让进程不向系统声明支持 Windows 8.1 / 10，版本探测类 API 会退化到兼容口径。 本报告未展开，可作为一个独立小项另查。

六、优化清单 必做叠加项 + 一项已定案

P0 / P1 / P2 是叠加项，彼此不冲突，也与配色无关； 末尾的配色与布局方向已定案（浅色自研 + 规则化），已不再是选择题。

P0-1补 manifest：启用 comctl32 v6 + PerMonitorV2最高性价比

怎么改（沿用 VoxType 已验证过的接线方式，三段式）：新增 src/app.manifest，声明 dpiAwareness = PerMonitorV2 与 Microsoft.Windows.Common-Controls 6.0.0.0 依赖； 在 src/voxmic.rc 里加 1 RT_MANIFEST "app.manifest"； CMakeLists.txt 给 voxmic 加链接选项 /MANIFEST:NO。

为什么必须同时做 v6 与 DPI：v6 解决"控件长什么样"，DPI 解决"清不清晰"， 两者共用同一份 manifest，分两次做等于改两遍文件、测两遍。

风险与必须验证的点：切到 v6 后所有控件改用视觉样式重绘，现有 WM_CTLCOLORSTATIC / EDIT / LISTBOX 的着色行为需要重新确认；代码里已有一条关于滑杆底刷的警告注释 （settings_dialog.cpp:1229-1232），必须实测滑杆是否出现黑条。 推断 切换后的实际观感需改前 / 改后各截一张同页面截图确认。

P0-2DPI 缩放：把裸坐标换成设计常量 + 缩放函数

怎么改：引入 DpiScaleForWindow() 与 S()（对齐 VoxType settings_controls.cpp:93-99 与 ui_utils.h:10-18），把散在 WM_CREATE 里的裸数字（25 / 64 / 92 / 120 / 205 …）抽成一张常量表， 所有创建调用统一包一层 S()；补 WM_DPICHANGED 重排。

字体同步：字号改为按 DPI 计算 -MulDiv(pt, dpi, 72)，不要再写死像素高度。

验收口径：在 100% / 125% / 150% 三档缩放下各截一张，要求文字边缘锐利、无位图拉伸痕迹。

P1-3统一字体：一套 Segoe UI，去掉混用

现在小节标题与提示用 MS Shell Dlg 写死 16px，其余控件从不设字体。 改为：正文 Segoe UI 9pt、小节标题 9pt Semibold，所有控件创建后都过一遍统一的 ApplyUiFont()（可照抄 VoxType hotkey.cpp:325-330）。 提示文字用灰阶差（而不是字号差）做层级。

MS Shell Dlg 是 GDI 的传统字体别名，推断 其映射目标不是 Segoe UI。本条未在本机复核 —— 读取字体映射表需要 reg.exe，该程序在本沙箱被安全策略拦截。 但不影响结论：无论映射到谁，硬编码 16px 都不随 DPI 与系统字体设置变化。

P1-4布局规则化（原"统一控件高度"，范围已扩大）核心

这一条已从"表层修补"升级为本次的核心。起因是：现在新增一个设置项要改 4 处（坐标 / 字体 / 加载 / 保存），任何一处漏掉就是 bug，且坐标靠人眼对齐 —— 这正是"以后新增选项又会全部自定义、导致混乱"的机制原因。只统一几个高度值治不了它。

做法：三层结构 —— metrics 常量表（唯一的尺寸来源，按 DPI 缩放）→ 字段表（每个设置项只声明"是什么"：id / label / kind / hint / dependsOn）→ 布局器（唯一一处算坐标，按声明顺序顺推）。同时把依赖态从三个手写 setter （现约 146 行）收成一次统一的 applyFieldStates()。

验收口径：新增一个设置项 = 只改 1 处（字段表加一条记录）， 不写坐标、不写 ShowWindow。完整设计（metrics 值、行高三档、字段表结构、 依赖态求值、新文件落点）见方案文档 §2。

P1-5补页脚区：分隔线 + 状态位 + 按钮靠右

VoxType 在 WM_PAINT 里用 DividerColor 画一条页脚分隔线，状态文字靠左、 按钮靠右，页脚位置由客户区高度推导（LayoutSettingsWindow）。我们现在是 4 个按钮平铺在 固定 y=490，窗口尺寸一变就错位。顺带补 WS_CLIPCHILDREN 消除切页闪烁。

P2-6键盘可达：补 Tab 序

加 WS_TABSTOP / WS_GROUP，窗口加 WS_EX_CONTROLPARENT 并在消息循环里走 IsDialogMessage。 注意 这是两边的共同缺陷，属独立改进，不算对标收益。

P2-7提示文字改用窗口属性标记

现在是维护一个 hintControls 向量再线性查找；VoxType 用 SetPropW 打标记、WM_CTLCOLORSTATIC 里查属性 （settings_controls.cpp:101-107），少一份需要同步维护的清单。顺手为之即可。

已定案配色 = 浅色，且自研 —— 不照抄 VoxType用户已决定

决定：配色走浅色，但不复制 VoxType 的色板 —— 按本项目自己的设计语言翻成浅色版本。 本项因此不再是二选一。落地色值见方案文档 §3：结构沿用已定的 4px 基准网格 / 11–17px 字号阶梯 / 4-8-14px 圆角 / 状态色绑定引擎真实状态，只把基色由深翻浅；深色基色作废，不留分支。

方向定案带来一个范围变化：既然 Slint 已放弃、Win32 设置窗口就是长期界面， 本次就不是"先做结构、配色留给将来的重写"，而是一次做到位 —— 并且把 布局规则化（字段表 + 布局器）当成核心来做，而不是"统一几个控件高度"这种表层修补。 依据见 §四：现在新增一个设置项要改 4 处（坐标 / 字体 / 加载 / 保存），这是"新增即混乱"的机制原因。

七、不建议照抄的部分

VoxType 的做法为什么不要抄
单文件 3448 行的设置界面，其中 SettingsWndProc 一个 switch 跨 1636 行（1782–3418） 比我们现在的 1458 行更糟。它"好看"和它"难维护"是两件独立的事，只抄前者。
18 个全局 std::vector<HWND> 控件分组，经头文件 extern 暴露 我们 B3 刚把 extern 从 30 清到 0 并收死守卫基线。抄回去等于架构倒退。
控件创建直接散在 WM_CREATE 内联展开 它在 settings_controls.cpp 里其实有一层不错的控件工厂，但主流程并未全部走工厂 —— 半途而废的做法不值得学。

八、建议的执行顺序 对应方案文档的 S1–S5

  1. S1+S2（manifest + DPI），一次提交。改前 / 改后各截一张设置窗口同页截图。 也是唯一能一次把"Win95 控件"变成"Win10 控件"的动作。
  2. S3（布局规则化），独立一次提交。判据是零视觉变化： 布局器摆出来的位置应与现在肉眼一致 —— 这样才能把"结构对不对"与"配色好不好看"分开验证。
  3. S4（浅色 token），替换全部系统色与硬编码色，验收要求无 COLOR_* 残留。
  4. S5（页脚 + 键盘可达），页脚分隔线与状态位、WS_TABSTOP 与 Tab 序。
  5. 顺手修计划文档：把 cxx23-slint-refactor-plan.md 的状态改到与事实一致（见 §六）。
